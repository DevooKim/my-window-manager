# 설정 저장·핫키 갱신 성능 개선 설계

## 목표

설정을 읽거나 변경할 때 메인 액터에서 발생하는 불필요한 디스크 저장과 전역 핫키 전체 재등록을 제거한다. 사용자 설정의 저장 형식과 실제 핫키 동작은 유지한다.

## 현재 문제

- `ConfigStore.load()`가 `didSet` 자동 저장 속성을 순서대로 대입한다. 저장된 값이 기본값과 다르면 읽기 동작 중에도 설정 파일을 최대 다섯 번 다시 쓸 수 있다.
- `AppDelegate`가 `ConfigStore.objectWillChange` 전체를 구독한다. 스냅 설정, 데드존, HUD 모양, 창 크기 비율처럼 핫키 등록과 관계없는 변경도 모든 전역 핫키를 해제하고 다시 등록한다.
- 편집 화면도 저장 직후 `HotkeyRegistry.rebuild()`를 직접 호출한다. 중앙 구독이 예약한 갱신과 겹쳐 한 번의 변경이 중복 재등록될 수 있다.
- 설정 가져오기는 여러 속성을 연속 대입하므로 자동 저장과 핫키 갱신이 변경 속성 수만큼 반복될 수 있다.

## 선택한 접근

`ConfigStore`가 실제 전역 핫키 등록 상태의 변경을 판별해 전용 신호를 보낸다. `HotkeyRegistry`는 저장소에 바인딩될 때 이 신호를 직접 구독한다.

대안으로 범용 변경 알림을 디바운스하거나 `HotkeyRegistry.rebuild()` 안에서 매번 전체 설정 스냅샷을 비교할 수 있다. 두 방식 모두 관계없는 변경이 갱신 경로에 진입하며, 후자는 모든 호출에서 비교 비용도 남는다. 전용 신호는 호출 자체를 제거하고 소유 경계를 저장소와 레지스트리에 한정한다.

## 구성 요소

### ConfigStore

- 등록 상태는 프리셋·레이아웃·사이클의 `id`와 `hotkey`, 이동·크기 액션의 `action`과 `hotkey`만으로 비교한다.
- 이름, 프레임, 레이아웃 배치, 사이클 구성, HUD 스타일, 스냅 설정, 데드존, 확대·축소 비율 변경은 등록 신호를 보내지 않는다. 핫키 핸들러가 실행 시점에 현재 모델 값을 조회하므로 재등록이 필요하지 않다.
- 설정 로드와 전체 가져오기는 부수효과를 억제한 채 모든 속성을 적용한다. 로드는 파일을 쓰지 않고, 가져오기는 적용이 끝난 뒤 정확히 한 번 저장한다.
- 묶음 적용 전후의 등록 상태가 다를 때만 핫키 변경 신호를 한 번 보낸다.

### HotkeyRegistry

- `bind(store:)`에서 저장소의 핫키 변경 신호를 구독하고 최초 한 번 등록 상태를 만든다.
- 일시 정지·재개 동작은 기존처럼 즉시 재구성한다. 핫키 캡처 중에는 등록을 비우고, 캡처가 끝나면 최신 저장 상태로 복원해야 하기 때문이다.

### 앱과 편집 화면

- `AppDelegate`의 광범위한 `objectWillChange` 구독을 제거한다.
- 프리셋, 사이클, 레이아웃, 이동·크기, 가져오기 화면의 수동 `rebuild()` 호출을 제거한다.
- 편집 화면은 저장소만 변경하고, 등록 갱신 책임은 저장소 신호와 레지스트리 구독에 맡긴다.

## 오류 처리와 호환성

- JSON 스키마와 기존 파일 위치는 바꾸지 않는다.
- 기존 저장 오류 처리 방식은 유지한다. 이 변경은 저장 실패 정책을 확장하지 않는다.
- 구버전 설정의 기본값 적용과 가져오기 결과는 그대로 유지한다.
- 초기 로드에서 설정 파일을 다시 쓰지 않으므로 사용자가 제공한 원본 바이트도 보존된다.

## 검증

- 비기본값이 든 설정 파일을 로드해도 파일 내용이 바뀌지 않는지 RED→GREEN 테스트로 확인한다.
- 핫키 조합이나 등록 대상이 바뀔 때만 신호가 한 번 발생하고, 이름·프레임·스냅 같은 비등록 변경에는 발생하지 않는지 확인한다.
- 전체 설정 가져오기가 디스크 저장과 핫키 신호를 각각 한 번만 수행하는지 확인한다.
- `make test`로 기존 전체 동작을 회귀 검증한다.
- 최종 diff에서 광범위 구독과 화면별 수동 재등록이 사라졌는지 확인한다.
